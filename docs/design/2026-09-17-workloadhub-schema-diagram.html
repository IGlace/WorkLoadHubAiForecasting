The WorkloadHub database with the forecast installed

For the developer of the WorkloadHub Spring Boot application: every table of the database as it stands once forecast-core is on the classpath, what the module adds to the schema and to the running application and what those additions mean, which of the application's tables and columns it reads and what they must contain, and the full guide to wiring it into the server and using its features from the server's own pages, the way the showcase forecast-web does. The forecasting logic itself, the features and how they are computed, is on the companion page The feature matrix, as it stands.

2 · What the forecast adds to the database

The module ships one Flyway migration and runs it into task_service, the application's own schema, at start-up, under its own history table forecast_schema_history, baselined at version 0 so that the application's tables are never created, altered or dropped by it, with one exception: two nullable columns on users. The schema gains seven tables and those two columns. No application table gets a foreign key pointing into the module, and the module writes to nothing but its own tables and the two columns.

One row per run: forecast_runs

Who asked (requested_by), for which team — team_id holds the leader's own users.id; the teams table is never involved — as of which day, the status the host shows as a progress label, the backtest result (mae in hours, backtest_json) and the error text when a run fails. Every other module table hangs off its id.

What a run computed: forecast_member_windows, forecast_member_days

Per member and window (five weekdays): predicted demand in hours with its low and high band, capacity, overload, working days, absence hours and two pressure figures (backlog excess, due excess). Per member and day: the week's demand placed on the day, the day's capacity and overload, and whether it is a working day. Kept per run, so past runs stay comparable with what was later logged.

The current forecast: forecast_current_days

The latest run's value per team, member and day, one row each. Each run upserts its days, so days ahead are overwritten and days that have arrived keep the last forecast made before them. This is what the calendar reads and what the accuracy check scores against time_logs.

What Copilot saw and wrote: forecast_facts, forecast_narratives

The exact facts JSON a run produced and Copilot was allowed to cite, one per run, kept for audit; and every narration attempt with its language, status (OK, UNVERIFIED, FAILED), the narrative and verification JSON, the raw answer, usage, attempts and tool calls. A failed narration keeps its row and its cost.

Two columns on users: the Copilot token

github_token holds the user's own GitHub token, encrypted with the key in whf.token-key; github_token_updated_at says when it was stored. The module reads the token in exactly one place, for the user who requested a narration, and never returns it. No other provider's key is ever stored.

How the module's tables join the application's

team_id, user_id and requested_by all hold users.id values (team_id the leader's), but the module declares no foreign key to users, so that a deleted or deactivated user never makes an old run undeletable or a migration fail. Nothing in the module points at teams. Inside the module every table references forecast_runs(id).

3 · What it reads, and what the data must contain

The forecast reads nine of the application's tables with plain SELECTs at the start of every run and writes to none of them. teams and team_members are not among them: they hold project teams, and the company structure the forecast needs is users.manager_id. This is the whole input: there is no feed to build and no event to send. What the application must do is keep these tables meaning what the forecast assumes they mean.

TableColumns readWhat the forecast does with them

What the data must contain

  • A member is a users row with active true whose effective role is MEMBER or TEAM_LEADER. Team membership is not a condition, and neither is users.role: the effective role comes from users.job_title — a title containing "skill team leader" or "center manager" makes an actor, one containing "team lead" or "lead engineer" makes a leader, anything else a member — and a leader with no counted direct report is a member. Only ADMIN, CENTER_MANAGER and VIEWER are read from users.role, because no job title implies them. Team leaders are forecast like members, because they do technical work. SKILL_TEAM_LEADER, CENTER_MANAGER, ADMIN and VIEWER are never forecast. deactivated_at ends the member's capacity; their history is kept.
  • A run is per team, and a team is a team leader and the people who report to them directly — users.manager_id. Its teamId is that leader's own users.id, not a teams row. The team's projects are the projects of its members' tasks; projects.team_id is not read. Archived projects and archived tasks are skipped.
  • Assignments must be written to task_history. Every change of assignee must produce a row with field_name assignee, new_value naming the new assignee (their full name; an e-mail, username or UUID is also resolved; empty, None or null means unassigned), changed_at, and user_id = the user who made the change. The forecast takes the assignment date from the latest such row that names the current assignee, and reads "self-picked" when that user_id equals the assignee, "assigned" otherwise. Without those rows it falls back to created_date and cannot tell how the task was assigned, and it reports the task as an unresolved assignment in the data-quality facts.
  • Status changes are read from task_history rows with field_name status and new_value the status name, only when tasks.started_date or finished_date is null. Every status must have a task_statuses.category of TO_DO, IN_PROGRESS or DONE.
  • Task types are read by task_types.name. The twelve names are grouped into families: Bug and Incident are defect work; Story, New Feature, Task, Improvement and Change Request are delivery; Spike, Test and Risk are support; Epic is a container; a Sub-task takes its parent task's family; a name the forecast does not know counts as delivery.
  • Estimates and dates on tasks: original_estimate_hrs in hours (the size of arriving work), remaining_estimate_hrs (shown to the leader as the hours still open), due_date, and planned_week as the Monday of the intended week (any other date is normalised to its Monday; null means unplanned). reopened_from_done marks rework. These five are read as they stand today; they have no history.
  • time_logs is the truth: hours per user, task and day. The forecast predicts exactly this, summed per member and week, and scores itself against it. Logging is not capped, so overtime shows up as it is.
  • Capacity is computed, not read. A member's week is whf.default-weekly-hours (44) times the week's working days over five, minus their approved leave hours; a working day is 8.8 h. user_capacity and team_capacity are not read.
  • Holidays: a holidays range with status CONFIRMED and active true removes its weekdays from everyone's calendar; a PENDING one is only mentioned in the narrative.
  • Leaves come from personal_leaves only (absences is not read). employee_id must be a users.id; the table declares no foreign key, so the application must guarantee it. status APPROVED reduces capacity, PENDING is listed for the narrative as a risk, REJECTED and CANCELLED are ignored. absence_hours is the total for the whole leave (null means every working day of the period); begin_time and end_time mark a leave that starts or ends on a partial day. The forecast deals the total over the leave's working days, 8.8 h a day, weekends and holidays skipped, the partial day last (or first when only begin_time is set).

Not read at all: teams and team_members (project teams), absences, user_capacity, team_capacity, task_comments, task_attachments, notifications, project_history, refresh_tokens, role_change_requests, sync_metadata, user_roles, job_titles, job_title_role_mappings. Names are used in the facts sent to Copilot (the member's full_name, the task key and title, project keys); UUIDs never leave the server.

4 · How to integrate it: the guide

The module is a library, not a service. The WorkloadHub server adds one Maven dependency and gets a ForecastService bean it calls from its own code; the server keeps its sessions, its roles and its pages, and writes a thin host layer between them and the module. This section is that guide, in the order the work is done: what the dependency changes in the application, what to configure, the host layer to write, the calls a page makes, what comes back, the routes to expose, the errors, running it, and testing it. The showcase forecast-web (server/forecast-web/) is the reference implementation of every step: it depends on forecast-core alone and does exactly what the server will, with an X-Acting-User header standing in for the session.

4.1 · What the dependency changes in the application

<dependency>
  <groupId>com.workloadhub</groupId>
  <artifactId>workloadhub-forecast-core</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>

Nothing else is required. The module's auto-configuration (ForecastAutoConfiguration, registered through META-INF/spring/…AutoConfiguration.imports, ordered after Spring Boot's own DataSource configuration and conditional on a DataSource bean) does the rest at start-up. These are the changes it makes to the running application, all of them visible and all of them replaceable:

The schema (section 2)

Flyway runs the module's one migration into task_service under its own history table, forecast_schema_history, baselined at version 0 so it never touches the application's migrations: seven tables and the two token columns on users. Set whf.flyway.enabled=false to run the same SQL (db/forecast/postgresql/V1__forecast_tables.sql in the jar) from the server's own migrations instead.

The beans

ForecastService and GitHubTokenStore are the two the server calls. Under them: a JdbcClient on the server's DataSource, CapacityRule, ForecastRunner, the run and narrative stores, RunProgressTracker, CopilotGateway, Narrator and a Clock. Every one is @ConditionalOnMissingBean: declare your own and the module uses it (the Clock and, in tests, the CopilotGateway are the two worth replacing).

Threads

A pool of whf.run-threads daemon threads (forecast-run) executes runs; startRun returns the id at once. Narration has no pool: narrate blocks on the caller's thread for the whole narration, so the host runs it on an executor of its own (4.4). Progress lives in memory, in the JVM that runs the run.

Files

whf.work-dir (default ~/.workloadhub-forecast) is the module's directory, and the Copilot home the SDK is given is <work-dir>/copilot. The SDK unpacks its in-process runtime once, on first use, under ~/.copilot/runtime-cache/<version>/ of the account the server runs as (about 91 MB, nothing downloaded). Both must be writable by that account; a service account without a home directory needs whf.work-dir set and a home it can write.

Start-up reconciliation

Once every bean exists, runs the previous process left QUEUED or RUNNING are marked FAILED (interrupted by a restart): a run cannot be resumed, only started again. A database that cannot answer is logged, never fatal.

The dependency tree

copilot-sdk-java 1.0.13-preview.6 with its linux-x64 runtime artifact (44 MB, runtime scope), JNA 5.19.1, and Jackson 2 (com.fasterxml) next to the server's Jackson 3 (tools.jackson); the two coexist under different package names, and Spring Boot's dependency management pins the Jackson 2 version. XGBoost4J needs the OpenMP runtime on the machine (libgomp1 on Debian). Spring MVC is optional and the servlet API is provided, so a host without them is unaffected; the PostgreSQL driver is the server's own.

What it does not change: no application table is altered but users, nothing is written to any of them, no event has to be raised and no feed built (section 3), and there is no scheduler. A run happens when the server calls startRun, whether from a page or from a schedule of the server's own; the module never starts one by itself.

Two more things belong in the server's configuration, and both are easy to miss because nothing fails at start-up without them:

  • A java.time.Clock bean in the server's time zone. The run day is "today" by that clock, and a run always starts from today: the horizon is the first weekday after it, so the zone decides which day that is around midnight. Without a bean the module uses the system default zone. A test pins a fixed clock the same way.
  • The connection's search path. The module names its schema when it migrates (task_service, written in ForecastMigrations), but every query it issues names its tables unqualified, so the connections it borrows from the server's DataSource must resolve task_service. The server's own connections already do, or it could not read its own tables. A connection that does not migrates cleanly and then fails the first request with relation "users" does not exist; currentSchema=task_service,public on the JDBC connection settles it (forecast-web's application.yml sets it through Hikari's data-source-properties).

4.3 · The host layer the server writes

The module deliberately leaves out everything that depends on the server's session. forecast-web's host package is that layer, written once so the server can copy it; only the first row below differs in production. Every class is small.

The effective role and the teams

The server must decide roles and teams the way the module does, or a page will offer a run the module refuses, or the reverse. Both rules are public in forecast-core, so the server calls them rather than re-implementing them. com.workloadhub.forecast.data.EffectiveRole is the role rule of section 3: the job title classifies, then a TEAM_LEADER with no counted, active direct report is demoted to MEMBER. It needs the user and their direct reports, nothing further out; the directory as a whole is simplest.

List<EffectiveRole.Candidate> rows = jdbc
        .sql("SELECT id, manager_id, role, job_title, active FROM users")
        .query((rs, i) -> new EffectiveRole.Candidate(rs.getObject("id", UUID.class),
                rs.getObject("manager_id", UUID.class), rs.getString("role"), rs.getString("job_title"),
                rs.getBoolean("active")))
        .list();
Map<UUID, String> role = EffectiveRole.resolve(rows);     // every user's effective role
boolean counted = EffectiveRole.counted(role.get(id), active);   // whether a run forecasts this user
boolean leadsATeam = "TEAM_LEADER".equals(role.get(id));  // then the team's id is this user's id

A team exists exactly when its key is an effective TEAM_LEADER; the module's own check (TEAM_NOT_FOUND otherwise) is the same test over the same rows. Its members are that user and every counted user whose manager_id is their id. A leader who reports to another leader is in two teams, their own and their manager's, and the two are two different runs. A counted user whose manager is a skill team leader, a centre manager or an admin is in no team and no run reaches them; the owner ruled that they stay out rather than being gathered under an actor, and the pages should show them as such rather than hide them.

Who may do what

The module trusts the requestedBy it is given; the server enforces the roles before calling it, and a refused check is the server's 403. The role is the effective one. An ADMIN, a CENTER_MANAGER and a SKILL_TEAM_LEADER lead no team of their own: they run on behalf of a leader beneath them, the first two for the whole organisation, the third for the leaders who report to them, one at a time.

Three predicates over users carry the whole table, as ForecastAccess writes them: manages (the user's id is the team id, and they are an effective leader), manages the leader of (the team's leader has manager_id equal to the user, and the user is a skill team leader), and member of (the user is the leader, or is counted and their manager_id is the team id). A team leader who reports to another team leader may not run the team beneath them: the middle predicate asks for a skill team leader, and the directory page must not say otherwise.

The facade's three rules

Besides the role check, the facade holds the three rules the module leaves to the host. First, a poll is authorised by asking the module which team the run belongs to: findRun(runId) answers for a run whatever its status, so the server keeps no table of its own and a restart loses nothing. Second, a skill team leader gets one run at a time, because they stand in for several leaders: latestRunOf(userId) gives their most recent run across every team, and its progress phase says whether it is still computing (anything but DONE, FAILED and the narration phases). The check and the start must be one step, or two clicks both pass. Third, narration runs on the host's own executor, one per run and language in flight, and the request returns at once.

public UUID startRun(ActingUser user, UUID teamId) {
    ForecastAccess.Decision d = access.run(user.id(), teamId);
    if (!d.allowed()) throw new HostForbidden(d.reason());                         // 403 with the reason
    synchronized (startLocks.computeIfAbsent(user.id(), k -> new Object())) {      // check-and-start, per user
        if (user.role().equals("SKILL_TEAM_LEADER")) {
            Optional<UUID> latest = service.latestRunOf(user.id()).map(RunSummary::id);
            if (latest.isPresent() && runInProgress(service.progress(latest.get()).phase()))
                throw new HostForbidden("one team at a time: run " + latest.get() + " is still in progress");
        }
        return service.startRun(new RunRequest(teamId, user.id()));                 // returns the id at once
    }
}

public Future<NarrativeResult> narrate(ActingUser user, UUID runId, String language, String model) {
    requireView(user, teamOf(runId));                       // teamOf = service.findRun(runId).teamId()
    if (!tokens.has(user.id())) throw ForecastException.of("TOKEN_MISSING", "...");   // one query, no session
    service.getRun(runId);                                  // RUN_NOT_FOUND or RUN_NOT_DONE before anything is queued
    String key = runId + "|" + language;
    if (!inFlight.add(key)) throw ForecastException.of("NARRATION_IN_PROGRESS", "...");
    return narrations.submit(() -> {                        // the host's own bounded executor
        try { return service.narrate(new NarrativeRequest(runId, user.id(), language, model)); }
        finally { inFlight.remove(key); }
    });
}

The in-memory lock and the in-flight set are enough for one instance, which is what the module supports (progress and the run pool live in the JVM). A server on several instances needs a database guard for both, and a shared progress store the module does not provide.

Keep the module's own controller off

whf.web.enabled stays false. The module's optional controller takes requestedBy from the request body and checks nothing, so with it on, anyone who can reach the port could start a run for any team and narrate with another user's stored token. forecast-web refuses to start with it on (WebSurfaceGuard), and keeps its own package outside com.workloadhub.forecast so component scanning never picks that controller up; the server should do both.

4.4 · The calls, in the order a page makes them

  1. Start a run. Check the role, then startRun(new RunRequest(teamId, userId)). It refuses a team whose key is not an effective leader (TEAM_NOT_FOUND), writes the run row as QUEUED and returns its id; the run executes on the module's pool. The run day is today by the clock, and a run covers the next whf.forecast.windows windows of five weekdays, starting the first weekday after today (a Friday or weekend run starts on Monday).
  2. Show progress. Poll progress(runId) about once a second and show label.en or label.fr; branch on phase. The phases and their labels: QUEUED "queued", LOADING "reading the team's data", FEATURES "preparing the history", BACKTEST "scoring the models", FORECAST "predicting the coming weeks", FACTS "assembling the facts", PERSIST "saving the run", then DONE "forecast ready" or FAILED "forecast failed" (the French is on the same record). percent is coarse; message is for logs. A run that finished in a previous process still answers from its stored status.
  3. Read the run. getRun(runId), for DONE runs only (RUN_NOT_DONE otherwise): the summary, the backtest scores, one row per member and window, one per member and weekday, and the facts JSON (4.5). listRuns(teamId, limit) is the team's history, newest first, at most 200.
  4. Show the team's calendar. currentForecast(teamId, from, to): per member and weekday, demand against capacity, from whichever run last covered the day before it arrived. It keeps answering while a newer run computes, which is why the team page reads it rather than the last run. Both dates are required and from may not be after to; the showcase defaults to today and today plus 20 days.
  5. Show accuracy. accuracy(teamId, from, to) compares what the current forecast said about each past weekday, before it arrived, with the hours logged on it. to is clamped to yesterday; nothing is stored, every call recomputes, and a range with no scored weekday comes back empty. Show it to whoever may view the team.
  6. Narrate. Check the role, GitHubTokenStore.has(userId) (one query) and that the run is DONE, then submit narrate(new NarrativeRequest(runId, userId, language, model)) to the host's executor and return. language is en or fr; model is null for the configured default. The page polls the same progress(runId): NARRATING with a label that rotates through "starting Copilot", "collecting data", "reading the forecast", "consulting Copilot", "thinking", "writing the report", "checking the numbers"; then NARRATED "report ready" or NARRATION_FAILED. Then read narrative(runId, language), the latest stored one. Every narration is stored whatever its status, so a failed one keeps its cost and its raw answer; a run may be narrated again, in either language.
  7. Tokens and the seat. A settings page calls GitHubTokenStore.save(userId, token) and clear(userId); has(userId) says whether one is stored, and nothing ever returns it. Accepted tokens are gho_, ghu_ and github_pat_; classic ghp_ tokens are refused with INVALID_REQUEST. The intended source is a GitHub OAuth App in the server, where the user signs in and the server stores what comes back; until then the token is pasted. copilotStatus(userId) opens a Copilot session with the stored token and reports the runtime, whether the token is accepted, the login and the remaining quota: it is the settings page's "check my seat" button, not a pre-check before every narration.

The facts (RunResult.factsJson, also stored in forecast_facts) are the exact document Copilot was allowed to cite, and a page can show them as the run's detail. Top level: run (id, as-of day, the windows with their working days, the origin week, the horizons), team (id and name of the leader, parent_team_id naming the skill team leader above them, demand and capacity totals per window), members[] (per member: thirteen weeks of history, the forecast rows with due_hours and planned_hours, the day rows, pending leaves, patterns, open tasks with keys, reopened and unlogged tasks, the last four weeks of logged hours, likely work), projects[] (the team's projects with open and backlog counts and first due date), model (name, target, mae and mean_actual_hours, confidence "scored" or "thin_history", the interval offsets, limitations, seconds by phase), rebalancing_candidates (overloaded, underloaded, backlog_pressed, deadline_pressed, each entry with the member's id, name and figure), pending_holidays and data_quality (unresolved assignments, unlogged tasks, history weeks). Members are named by full_name and tasks by key, since that is what the narrative cites; ids are there for joining.

4.7 · Errors

Every module error is a ForecastException with a stable code() and a message safe to show. The mapping forecast-web uses, and the module's own controller shares, is by code shape, so a new code needs no new handler:

StatusCodesWhose
401ACTING_USER_MISSING, ACTING_USER_UNKNOWNthe host's session stand-in; the server's own sign-in replaces them
403FORBIDDENthe host: a refused role check, or one run at a time; the message carries the reason
404TEAM_NOT_FOUND, RUN_NOT_FOUND, USER_NOT_FOUND, NARRATIVE_NOT_FOUNDthe module: any code ending in _NOT_FOUND
400INVALID_REQUESTthe module: a missing field, a bad date range, a language other than en or fr, a refused token prefix; the host adds a malformed body or a path variable that is not a UUID
409RUN_NOT_DONE, TOKEN_MISSING, TOKEN_KEY_MISSING, TOKEN_REJECTED, COPILOT_UNAVAILABLE, NARRATION_IN_PROGRESSevery other module code: a state that forbids the action; NARRATION_IN_PROGRESS is the host's

A failed run is not an exception to the caller: startRun returned its id, and the failure is on the run row (status FAILED, error) and in progress. A narration that times out or produces no usable text is likewise a stored NarrativeResult with status FAILED, not an exception; narrate throws only when it could not start (no token, run not done, Copilot unreachable, token rejected).

4.8 · Running it

  • One instance. Progress, the run pool and the facade's guards live in the JVM. Two instances would each run and each reconcile the other's runs as interrupted at start-up.
  • A run's cost. Every run reads the whole history of every counted user (65 weeks back), builds the feature matrix and fits the models once, then derives the chosen team; the per-team work is the small part. Measured on 2026-09-22 against a 264-user export with a year of history:
WhatMeasured
a run for a 25-member team78 s, confidence scored, MAE 5.67 h over 11 backtest scores
the import behind it31,520 tasks, 121,568 logs, 36 s
accuracy over the fortnight before the run225 rows, MAE 1.85 h, MASE 1.084
  • Scheduling is the server's. A nightly run per team, started with the leader as requestedBy, gives every leader a fresh calendar each morning and feeds the accuracy page; the module only runs when asked.
  • The token key is a secret with the lifetime of the stored tokens: rotating it makes every stored token unreadable, and users store theirs again. A missing key stops nothing but narration and token storage.
  • The work directory holds the Copilot runtime and nothing the server needs to back up. Sessions never resume: each narration is one client and one session, closed at the end.
  • What leaves the server is the facts document, sent to Copilot through the user's own seat, and it is stored in forecast_facts for audit. Real names are in it (owner decision); UUIDs are not. No other provider's key is ever stored, and the language model never produces a forecast number.
  • The real database is never seeded. The seed, the import and the experiment driver are in forecast-tools, which is never shipped and only ever targets the local PostgreSQL of scripts/postgres.sh.

4.9 · Testing the host

No test talks to Copilot. The module's CopilotGateway bean is @ConditionalOnMissingBean, so a test configuration declares a scripted one and every narration path runs end to end without a token or a network: the sample host in the module's own tests (forecast-core/src/test/java/…/samplehost/) is a @SpringBootApplication with a DataSource, a fixed Clock and a FakeGateway bean, driven through MockMvc. forecast-core's test-jar carries the seeded fixture (SeededData, a PostgreSQL started by Testcontainers and filled from fixtures/seeded-rows.sql) and that fake gateway, which is what forecast-web adds as a test dependency to run one ordered integration test over its whole REST surface (ForecastWebIntegrationTest): a run to DONE, the current forecast, accuracy after the clock moves, a narration through the scripted gateway, the tokens, and every refusal of the role matrix with its reason. The server's tests can do the same with the same two dependencies. The live path is checked by hand, with a real token, on the showcase's Copilot page or with the sample host below.

4.10 · Try it before writing code
