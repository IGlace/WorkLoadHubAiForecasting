2 · What the forecast adds to the database

The module ships one Flyway migration and runs it into task_service, the application's own schema, at start-up, under its own history table forecast_schema_history, baselined at version 0 so that the application's tables are never created, altered or dropped by it, with one exception: two nullable columns on users. The schema gains seven tables and those two columns. No application table gets a foreign key pointing into the module, and the module writes to nothing but its own tables and the two columns.

One row per run: forecast_runs

Who asked (requested_by), for which team — team_id holds the leader's own users.id, and the module declares no key to teams — as of which day, the status the host shows as a progress label, the backtest result (mae in hours, backtest_json) and the error text when a run fails. Every other module table hangs off its id.

What a run computed: forecast_member_windows, forecast_member_days

Per member and window (five weekdays): predicted demand in hours with its low and high band, capacity, overload, working days, absence hours and two pressure figures (backlog excess, due excess). Per member and day: the week's demand placed on the day, the day's capacity and overload, and whether it is a working day. Kept per run, so past runs stay comparable with what was later logged.

The current forecast: forecast_current_days

The latest run's value per team, member and day, one row each. Each run upserts its days, so days ahead are overwritten and days that have arrived keep the last forecast made before them. This is what the calendar reads and what the accuracy check scores against time_logs.

What Copilot saw and wrote: forecast_facts, forecast_narratives

The exact facts JSON a run produced and Copilot was allowed to cite, one per run, kept for audit; and every narration attempt with its language, status (OK, UNVERIFIED, FAILED), the narrative and verification JSON, the raw answer, usage, attempts and tool calls. A failed narration keeps its row and its cost.

Two columns on users: the Copilot token

github_token holds the user's own GitHub token, encrypted with the key in whf.token-key; github_token_updated_at says when it was stored. The module reads the token in exactly one place, for the user who requested a narration, and never returns it. No other provider's key is ever stored.

How the module's tables join the application's

team_id, user_id and requested_by hold the application's own UUIDs, but the module declares no foreign key to teams or users, so that a deleted or deactivated user never makes an old run undeletable or a migration fail. Inside the module every table references forecast_runs(id).

3 · What it reads, and what the data must contain

The forecast reads eleven of the application's tables with plain SELECTs at the start of every run and writes to none of them. This is the whole input: there is no feed to build and no event to send. What the application must do is keep these tables meaning what the forecast assumes they mean.

TableColumns readWhat the forecast does with them

What the data must contain

  • A member is a users row with active true and role MEMBER or TEAM_LEADER. That is the whole test: team membership is not a condition. Team leaders are forecast like members, because they do technical work. SKILL_TEAM_LEADER, CENTER_MANAGER, ADMIN and VIEWER are never forecast. deactivated_at ends the member's capacity; their history is kept.
  • A run is per team, and a team is a team leader and the people who report to them directly — users.manager_id. Its teamId is that leader's own users.id, not a teams row. The team's projects are the projects of its members' tasks; projects.team_id is not read. Archived projects and archived tasks are skipped.
  • Assignments must be written to task_history. Every change of assignee must produce a row with field_name assignee, new_value naming the new assignee (their full name; an e-mail, username or UUID is also resolved; empty, None or null means unassigned), changed_at, and user_id = the user who made the change. The forecast takes the assignment date from the latest such row that names the current assignee, and reads "self-picked" when that user_id equals the assignee, "assigned" otherwise. Without those rows it falls back to created_date and cannot tell how the task was assigned, and it reports the task as an unresolved assignment in the data-quality facts.
  • Status changes are read from task_history rows with field_name status and new_value the status name, only when tasks.started_date or finished_date is null. Every status must have a task_statuses.category of TO_DO, IN_PROGRESS or DONE.
  • Task types are read by task_types.name. The twelve names are grouped into families: Bug and Incident are defect work; Story, New Feature, Task, Improvement and Change Request are delivery; Spike, Test and Risk are support; Epic is a container; a Sub-task takes its parent task's family; a name the forecast does not know counts as delivery.
  • Estimates and dates on tasks: original_estimate_hrs in hours (the size of arriving work), remaining_estimate_hrs (shown to the leader as the hours still open), due_date, and planned_week as the Monday of the intended week (any other date is normalised to its Monday; null means unplanned). reopened_from_done marks rework. These five are read as they stand today; they have no history.
  • time_logs is the truth: hours per user, task and day. The forecast predicts exactly this, summed per member and week, and scores itself against it. Logging is not capped, so overtime shows up as it is.
  • Capacity is computed, not read. A member's week is whf.default-weekly-hours (44) times the week's working days over five, minus their approved leave hours; a working day is 8.8 h. user_capacity and team_capacity are not read.
  • Holidays: a holidays range with status CONFIRMED and active true removes its weekdays from everyone's calendar; a PENDING one is only mentioned in the narrative.
  • Leaves come from personal_leaves only (absences is not read). employee_id must be a users.id; the table declares no foreign key, so the application must guarantee it. status APPROVED reduces capacity, PENDING is listed for the narrative as a risk, REJECTED and CANCELLED are ignored. absence_hours is the total for the whole leave (null means every working day of the period); begin_time and end_time mark a leave that starts or ends on a partial day. The forecast deals the total over the leave's working days, 8.8 h a day, weekends and holidays skipped, the partial day last (or first when only begin_time is set).

Not read at all: absences, user_capacity, team_capacity, task_comments, task_attachments, notifications, project_history, refresh_tokens, role_change_requests, sync_metadata, user_roles, job_titles, job_title_role_mappings. Names are used in the facts sent to Copilot (the member's full_name, the task key and title, project keys); UUIDs never leave the server.

4 · How to integrate it

The module is a library, not a service. The server adds one dependency; Spring Boot's auto-configuration finds the server's own DataSource, runs the migrations of section 2 and registers the ForecastService bean, the token store, the run executor and the Copilot gateway. Every bean is @ConditionalOnMissingBean, so the server can replace any of them.

<dependency>
  <groupId>com.workloadhub</groupId>
  <artifactId>workloadhub-forecast-core</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>

Properties

Declare a java.time.Clock bean in the server's time zone: the run day is "today" by that clock, and a run always starts from today (an asOf in a request is refused). Without one the module uses the system default zone.

The calls, in the order a page makes them

  1. Start a run. startRun(new RunRequest(teamId, userId)) returns the run id at once; the run executes on the module's pool. Persist (runId, teamId, requestedBy) in a table of your own: after a restart that row is what lets you authorise a poll of an interrupted run.
  2. Show progress. Poll progress(runId) and show label (en and fr) until the phase is DONE or FAILED. The phases are the run's steps: loading, features, backtest, forecast, facts, persist. Runs left QUEUED or RUNNING by a previous process are marked FAILED at start-up; progress lives in one JVM.
  3. Read the result. getRun(runId) gives the run, its backtest scores, the member windows (demand, band, capacity, overload, pressure) and the member days, plus the facts JSON. currentForecast(teamId, from, to) gives the calendar view: per member and day, demand against capacity, from whichever run last covered the day. listRuns(teamId, limit) lists past runs.
  4. Show accuracy. accuracy(teamId, from, to) compares the forecasts made before each past weekday with the hours logged on it and scores them by team, member and horizon. Nothing is stored; every call recomputes.
  5. Narrate. Requires a DONE run and a token for the requesting user (GitHubTokenStore.has(userId)). narrate(new NarrativeRequest(runId, userId, language, null)) blocks for the whole narration, a minute or more, so submit it to a bounded executor of your own and let the page poll progress(runId) (NARRATING with a rotating label, then NARRATED or NARRATION_FAILED) and read narrative(runId, language). Copilot reads the facts through nine tools and writes English or French; every number it writes is checked against the facts, and a number that cannot be found is reported as UNVERIFIED, never hidden. Refuse a second narration of the same run and language while one is in flight.
  6. Tokens. A settings page calls GitHubTokenStore.save(userId, token) and clear(userId), and shows copilotStatus(userId), which opens a Copilot session and reports authentication and quota. Accepted tokens are gho_, ghu_ and github_pat_; classic ghp_ tokens are refused. The intended source is a GitHub OAuth App in the server, where the user signs in and the server stores what comes back.
  7. Errors. ForecastException.code(): a code ending in _NOT_FOUND is a 404, INVALID_REQUEST a 400, everything else (RUN_NOT_DONE, TOKEN_MISSING, TOKEN_KEY_MISSING, TOKEN_REJECTED, COPILOT_UNAVAILABLE) a 409.

With whf.web.enabled=true the same calls exist as REST routes under the base path: POST /runs, GET /runs/{id}, GET /runs/{id}/progress, GET /teams/{teamId}/runs, GET /teams/{teamId}/current?from&to, POST /runs/{id}/narratives, GET /runs/{id}/narratives/{lang}, GET /copilot/status?userId, PUT and DELETE /users/{id}/github-token. Authorisation stays the server's. The reference implementation of all of the above is the sample host in the module's tests (samplehost/: a facade with the role checks, the one-run-at-a-time rule and the narration executor) and HostExample in forecast-tools (server/examples/run-host-example.sh), which makes every call against a seeded database and prints what comes back.

What the dependency brings with it: copilot-sdk-java with its 44 MB in-process runtime (unpacked once under the work directory, nothing downloaded at run time), JNA, and Jackson 2 beside the server's Jackson 3; the two coexist under different package names. Spring MVC is optional and only used when the REST controller is enabled.
