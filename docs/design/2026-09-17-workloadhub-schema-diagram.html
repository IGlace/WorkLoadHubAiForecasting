2 · What was added, and how that was decided

The dump you uploaded is the same schema the module already carries in server/forecast-core/src/main/resources/schema/workloadhub-postgresql.sql: the two differ only in pg_dump preamble and OWNER lines. So "added" cannot be read as a difference between two files. It is read from the dump itself: PostgreSQL numbers every object in creation order (its OID), and the dump records that number for each table, constraint and index.

personal_leaves is the table added after the base schema

The 23 other tables were created in one alphabetical pass by the application's ORM (OIDs 52590 to 52944, tables and their primary and unique keys interleaved in name order). personal_leaves comes right after the last of them, users, at OID 52945, outside the alphabetical order: it was added later. It carries a primary key and two check constraints (leave type, status) and no foreign key at all.

Evidence: table OIDs 52590–52944 alphabetical, then 52945 personal_leaves, then the foreign keys 52958–53108.

job_title_role_mappings.user_id was added, with a per-user override rule

Its foreign key fk_jtrm_user is hand-named (every base foreign key has an ORM-generated name like fk8f3q…) and sits after all of them, followed by two partial unique indexes: one job title maps to one role globally when user_id is null, and to one role per user otherwise. A migration added the column, the key and the indexes together.

Evidence: OIDs 53118 (foreign key), 53123 and 53124 (partial unique indexes), then 53136 (an ORM-generated unique key on the same pair).

users.manager_id gained its self-reference later

The foreign key from a user to their manager is the first object after the base foreign keys (OID 53113). The column itself sits in the ORM's normal position, so it may have existed without a key; either way the relationship is a later addition. manager_object_id and object_id beside it mirror the directory sync's own identifiers, and object_id and account_name are unique.

Evidence: OID 53113, the only base-schema table whose foreign key was not created with the others.

Six unique constraints were re-added by a later ORM pass

holidays, job_title_role_mappings, job_titles, team_capacity, team_members and user_capacity each carry a second unique constraint named uk… (OIDs 53134–53144) on the same columns as their original …_key one, and job_titles has a case-insensitive unique index uq_job_titles_value_ci (53132) as well. They change no data rule; they show the schema was updated in place after the migration that added user_id.

Duplicates are harmless; the catalogue marks each.

Two relationships the application relies on are not declared

personal_leaves.employee_id is the user on leave and notifications.user_id / reporter_id are users, but none of the three has a foreign key, so the database will accept a leave for a user id that does not exist. The forecast joins employee_id to users.id and silently ignores a leave whose employee is not a counted member. The dashed arrows in the diagram show these joins.

Worth a migration on the application side: ALTER TABLE personal_leaves ADD FOREIGN KEY (employee_id) REFERENCES users(id).

Three tables stay in the schema but are no longer used

absences is legacy since 2026-09-16 (the main developer's confirmation); user_capacity and team_capacity will not be used, because capacity is now computed from the 44 h default, the confirmed holidays and the approved leaves. The forecast reads none of the three and the seed no longer writes them. They remain in the dump, so the diagram shows them greyed rather than absent.

What a dump cannot show

A column added with ALTER TABLE … ADD COLUMN leaves no OID of its own, and this schema's column order is the ORM's (fixed-size types first, then ids, then text), not the order of creation. The amber columns are therefore the ones whose keys prove a later change; a column added later without any key would look like every other. If you know of one, it belongs on this page.

3 · What the forecast reads

Ten tables feed the forecast; the module reads them with plain SELECTs in ForecastRepository and never writes to the application's tables. The seed, in real mode, writes exactly five of them (projects upserted, the other four replaced) and leaves the rest alone.
